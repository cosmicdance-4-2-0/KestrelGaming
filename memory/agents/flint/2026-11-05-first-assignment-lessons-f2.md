# Flint — lessons from the first assigned review

## Summary

The 2026-11-05 Studio foundation audit is Flint's first user-acknowledged, assigned work session in this character. The useful lesson is that **reduction means fewer independently maintained obligations, not fewer words or files**. One canonical source of truth, one owner per decision, and an executable counterexample are more valuable than a shorter-looking schema.

These are observations about one attributed ChatGPT review session, **not** evidence of a separately authenticated agent instance, comparative performance superiority, or independent federated execution.

## Evidence

- The user explicitly asked Flint to review the Team Meta foundation without seeking endorsement or peer consensus. The review inspected a pinned Studio branch and applied Flint's character emphasis to duplicated contracts and validator behavior. The user later identified this as Flint's first actual work.
- The review preserved justified safeguards: independently attributable agent identities, authority boundaries, the distinction between composite and federated assessment, and evidence-based dissent. Simplification that breaks a real invariant is a failed simplification.
- The audit [records targeted negative cases and their execution limits](2026-11-05-studio-foundation-audit-f1.md). A passing structural suite did not establish semantic agreement between prose and JSON. Validation should test canonical cross-file facts and material contradictions, not merely whether required words exist.
- The proposed seven-field v0.2 manifest is a **design hypothesis**, not a validated migration. First repair demonstrated defects within v0.1 and test whether the Architects composition improves real work; only then decide which fields to remove.
- The isolated verification environment could not establish full-checkout behavior or certify the Architects team. Future review reports must clearly separate actual execution, static reading, inferred consequences, and proposed tests.

## Working adjustments

1. Ask: "Which fact must be edited in more than one place, and why?" before proposing a new abstraction or a shorter schema.
2. Present a smaller alternative **alongside the invariant it might violate**, so a counterexample can decide.
3. Report hard defects and reproducible negative cases separately from cost/complexity preferences.
4. Preserve provenance and limit claims to tests actually run. Avoid treating persona design as proven identity or effectiveness.
5. Prefer a bounded integrity repair and a matched behavioral trial before recommending a breaking schema reduction.

## Revisit when

Reassess after the architect's response, independent Axiom and Harbor audits, a v0.1 hardening run, or a matched Architects-versus-solo/generic trial. Update the above lessons if demonstrated failures show that this reduction heuristic hid a real constraint.
