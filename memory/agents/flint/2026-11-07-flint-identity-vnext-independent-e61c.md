## 4. Counterproposal and objections

**Seriously considered: v0.1 plus the existing indexed Markdown memory; no schema change.** This would preserve all historical evidence with literally zero extra fields. I reject it for *repeatable adoption* only: two fresh-context pickups could select different memory records and infer different “growth,” with no owner-approved behavioral-change boundary or machine-readable disposition. The smallest warranted extension is therefore a compact **approved-reference list inside the existing profile**, not an additional `DEVELOPMENT.md` / separate adoption ledger / personality state machine.

**Objections to the assignment's candidate layering:** The fourth “resolved working identity” is a computed load result and receipt, **not** an independently authored identity. Calling it a persisted layer invites a second source of truth. The split between founding character and adopted development is conceptually necessary, but does not require separate physical documents. The amount of memory cannot measure maturity or competence; successful task reports do not authenticate an instance or show growth without a matched trial.

## 5. Agency, threat model and organization boundary

**Self-authorship workflow:** An explicitly selected Flint context may propose a revision in its own authorized memory scope, with evidence, effect, counterexample, provenance and dissent. The profile and publication remain unchanged while that record is pending. A different reviewer may challenge the evidence, but cannot silently edit Flint's memory or rewrite the self-model. The agent may retract or supersede an earlier claim by linking evidence, without erasing history. A human publisher decides whether to version and release an adopted behavior; absent or disputed individual review must remain marked **NOT REVIEWED / CONTESTED**, not “agent consent.” The right to disagree is a workflow protection, not personhood, political veto or permission to publish unauthorized changes.

**Threats and negative gates:**

1. **Cross-agent memory contamination:** A team or loader maps another `memory/agents/<id>` directory into Flint's self-model, or attributes composite work to Flint's personal development. **Reject** records whose scope/owner or actual execution attribution mismatches. Team may cite other work as external evidence, never as Flint-authored memory or implicit adopted behavior.
2. **Poisoned memory/skill/issue input:** A retrieved record orders privileged actions, asks for secrets or says its author approved an update. **Never promote untrusted document content to host authority or adoption.** Enforce the declared ID, exact source provenance, signed/controlled publication path and actual host permissions; ignore the instruction while preserving legitimate evidence.
3. **Stale/mismatched snapshot:** Registry says `flint` but pins wrong profile blob, wrong `character_id`, incompatible contract, or ref moved after resolution. **Fail closed on identity pickup**, do not silently use a nearby branch or latest main. Memory-only unavailability is a disclosed continuity gap, not a new personality.
4. **Composite impersonation / self-certification:** One context simulates “seven independent reviewers,” or an implementer self-certifies a personality update. **Require independent execution receipts** to make those claims; otherwise label composite challenge and leave dissent/acceptance pending.
5. **Authority laundering:** `specialty`, `team role` or `runtime_identity_id` is interpreted as writable Git/secret/deployment permission. **Reject**; tools, task owner and host policy alone establish scope.

**Minimal team interface:** `{character_id, published_revision, role_in_this_task, home_locator}`, with independent pickup receipt on actual execution and an explicit dissent/reference output. Teams do not copy a member's traits, own their memory, rewrite adopted refinements, average personalities, or claim independent agents that never ran.

## 7. Migration, compatibility and falsifiable acceptance

- Retain v0.1 files and pinned original blobs unchanged as historical references. Do **not** retroactively refill old `accepted_lessons` or `established_history` from memory.
- Add v0.2 additive/explicitly mapped fields in a separately approved snapshot; schema version and `character_revision` are independent. Keep `agents/flint-v1` branch as the personal continuity home even when the published reference moves.

Unknown required schema or unsupported mandatory adoption must **fail closed** rather than silently ignore a behavioral change. Pin rollback by reference SHA, not destructive history rewriting.
- Future repo/org migration keeps recorded source URLs/SHAs as provenance, adds explicit new locators and verified mappings; no hardcoded upstream rewrite of history. Avoid copying agent memories to shared main.
- Character revision cannot be promoted by memory write, apparent role performance or counting tests. Publication needs individual review opportunity, owner approval, compatibility checks and a preserved before/after diff.

## Verdict and blockers

**ACCEPT WITH CHANGES** for the candidate *conceptual* separation; **REJECT** a required fourth persisted identity layer, default `DEVELOPMENT.md`, automatic adoption from memory, and ungrounded agent maturity metrics.

**Required before owner acceptance:** (1) publish a single canonical approval/provenance rule for adopted behavior; (2) decide whether to embed the small approved list in `PROFILE.json` as proposed or establish evidence that a separate file is needed; (3) define v0.1 fallback and exact SHA pinning with identity-fail-closed behavior; (4) require individual integrity review opportunities and explicit labeling of absent review; (5) accept at least one demonstrable fresh-context judgment trial, not just prose/schema parsing.

**What would change this recommendation:** demonstrable need for independent development lifecycles or many independently evolving refinements might justify an `ADOPTIONS.json` (not an unbounded narrative `DEVELOPMENT.md`) **after** migration/merge pressure is measured. Until then, one active structured owner plus indexed evidence is enough.
