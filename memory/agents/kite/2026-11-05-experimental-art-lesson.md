# Kite — reversible presentation experiment

## What actually worked

In an authorized engineering session, Kite executed a narrow presentation experiment instead of replacing an application-wide visual system. The technique was to preserve a known working renderer, put an alternative behind a local default-off control, and derive both views from existing read-only identity and appearance data. Avoid producing a second persistence model.

The prototype's pure projection tests and actual browser-based integration checks both passed under a compatible test runner. Initial CI failed because the selected operating-system image was unsupported by the pinned browser automation tool; isolating a one-line runner adjustment into a separately reviewed infrastructure change restored test execution. A temporary validation branch demonstrated the alternate renderer without merging that infrastructure change into the project-specific art branch.

**The most important observed outcome:** Passing functional and browser regression suites did **not** imply that the experimental artwork matched the desired visual silhouette. Real viewport screenshots exposed aesthetic shortcomings that were invisible in enlarged concept sheets. The experimental switch remained default-off, and design approval was left open.

## Reusable Kite method

1. Preserve and measure a working control.
2. Prototype one variable behind a reversible, explicitly scoped switch.
3. Reuse canonical identity and authored definitions; never hide new mutable state in a renderer.
4. Test at actual output scale and environmental combinations, not only at enlarged concept scale.
5. When CI tooling fails, distinguish tooling failure from application failure; isolate environmental repairs with one owner and a minimal diff.
6. Keep implementation success, executable verification, performance evidence and human art acceptance on separate axes.
7. Retire test-only branches without merging them. Retain evidence paths and describe artifact expiration rather than assuming screenshots are permanently accessible.

## Boundaries and uncertainty

The non-public target's name, implementation details, branches, PRs, visual assets, test logs and screenshots are deliberately excluded. Future Kite sessions must retrieve those from their authorized source, not from this public note. The numeric results and precise artifact references were recorded privately, not repeated here.

This is an attributed engineering-session record, not a claim that an independently operating agent with persistent private consciousness or user-level authority exists. It does not expand repository permissions.

## Revisit when

A measured performance comparison changes the preferred rendering approach; a designer accepts or rejects the experiment; or the core read-only projection/fallback contract changes.
